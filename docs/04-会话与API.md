# 04 会话与 API

## 1. 会话模型

一次会话 = 一个学习者在一道题上的工作区，内含**两个独立的 VM 实例**，状态保存在服务端内存中。MVP 不做持久化，服务重启后会话丢失。

| 实例 | 作用 | 可交互 | 判胜后果 |
|---|---|---|---|
| **调试实例** | 草稿纸：随便写、单步、回退、重来 | 是 | 只提示“当前状态已满足成功条件”，不发 flag、不记录 |
| **判题实例** | 证明用：提交时重置到初始状态，回放 payload | 否 | 判胜即下发 flag，**记录不可撤销** |

这映射真实 pwn 流程：gdb 里反复调，写出 exploit，然后打一次远端。

**提交为什么不是多余的仪式。** 调试实例里允许做 payload 之外的事——手动写几次字节、单步数偏移。这些手工动作不在 payload 里。提交要证明的是：**光靠这份 payload，从初始状态出发就能赢**。手工试出来的认识必须落回积木。

- 两个实例的动作集完全一致。调试模式不提供判题时没有的能力，否则学习者会用一种提交时用不上的手段“解出来”。
- 提交次数不限。失败就回调试模式继续——这是学习，不是考试。
- 调试实例的任何操作不影响判题实例，反之亦然。
- 实例内的动作**串行执行**：同一会话同一时刻只处理一个请求，用每会话锁实现。
- 空闲 30 分钟的会话会被回收。

### 1.1 状态

调试实例有四种状态：

| 状态 | 含义 |
|---|---|
| `ready` | 可继续执行 |
| `satisfied` | 当前状态已满足成功条件。**不是通过**，只是提示 |
| `failed` | 运行时异常，或命中失败条件 |
| `exited` | 程序已结束但未满足成功条件 |

- 处于 `failed` 或 `exited` 时，执行类动作被拒绝，回退类动作仍可用。`satisfied` 不限制任何动作。
- 调试实例里没有 `won`：判胜只属于判题实例，它不是一个可停留的会话状态，而是一次提交的结果。

MVP 不做 revision、baseRevision、幂等键和 clientSeq。前端串行发送请求即可，“刷新页面”通过 `GET` 当前状态恢复。

## 2. 动作

| 动作 | 参数 | 类别 |
|---|---|---|
| `write_bytes` | `addr`, `hex` | 写原语 |
| `push` / `pop` | `value` / — | 写原语 |
| `call` / `ret` | `addr` / — | 写原语：直接操纵栈与 ip，**不执行指令** |
| `feed` | `hex` | 往 stdin 缓冲追加字节，**不执行指令**，见 02 §5.3 |
| `block` | `id`, `args` | 出题人积木，服务端展开为上面几类原子动作 |
| `step` | `count?` | 执行 N 条指令，默认 1 |
| `run` | `maxSteps?` | 连续执行，直到程序退出、异常或达到步数上限 |
| `undo` | — | 回退上一次提交 |
| `step_back` | — | 回退一条指令（仅调试实例） |
| `reset` | — | 回到初始状态（可被 undo） |

- 题目通过 `allowedActions` 限定可用动作。回退类动作始终可用，不受 `allowedActions` 约束。
- **MVP 没有断点。** 题目只有几条指令，`step` 就够用；`run` 退化成“我看够了，跑完它”。
  - 代价是循环类题目不好观察：单步太慢，`run` 会冲过头。所以 `step` 带 `count`，`run` 带 `maxSteps`，界面上暴露成“运行 N 步”。
  - 断点原本用来“停在 ret 之前”。现在的替代手段是冲过去再 `step_back` 倒回来，见 §3。
- 写原语在执行前做校验：
  - 写入的地址段必须完全落在已映射、非隐藏、可写的 VMA 内。
  - `pop` / `ret` 会从栈上读值，所以读取的栈槽同样必须落在已映射、非隐藏、可读的 VMA 内。否则 `pop` 就成了读隐藏内容的通道。
  - 不满足时**拒绝**（`rejected`），状态不变，不压快照。
  - 错误码：未映射或越权为 `inaccessible_address`，落在隐藏 VMA 为 `hidden_address`。布局是公开的，区分二者不泄露任何内容，反而有教学价值。
- `feed` 后 stdin 缓冲累计超过 4KB 时拒绝。
- 已执行的动作若触发指令异常，实例进入 `failed`。

## 3. 回退

调试实例是草稿纸，**reset 才是主要的脱身手段**——犯错不要紧，重来是免费的。所以回退的职责不是“救我”，而是“让我再看一遍”。三层：

| 层 | 操作 | 粒度 | 范围 |
|---|---|---|---|
| 初始 | `reset` | 回到题目初始状态 | 永远可用 |
| 请求 | `undo` | 回退上一次提交 | 完整历史，到快照上限为止 |
| 指令 | `step_back` | 回退一条指令 | 最近 N 条，环形缓冲，默认 N=64 |

- **请求层**：每个 `actions` 请求在执行第一个动作前压入一份 COW 快照。一次请求一次撤销，无论它含几个动作。
- **指令层**：`step` 和 `run` 执行期间，每条指令前额外压一份轻量快照，进环形缓冲。
  - 这一层专为“ret 刚执行完，rip 跑到了奇怪的地方，给我看前一瞬间”而存在。断点没了之后它从锦上添花变成主要手段。
  - 单条快照约 4–8KB（脏页 + 寄存器），N=64 时单会话 256–512KB，百人并发 25–50MB。
  - 环形缓冲满了丢最旧的。退到窗口之外就只能用 `undo` 或 `reset`。
  - 实现上复用同一套 COW 机器，只是多一条缓冲策略。
- `undo` 和 `step_back` 自身不压栈，否则无法连续后退。`reset` 压栈，因此可被撤销。MVP 不做 redo。
- 历史为空时回退被拒绝。超出快照上限时丢弃最旧的。
- **`failures` 不随回退减少。** 它是“这个人挣扎了多少”的度量，喂给提示解锁。否则反复 undo 就永远解不开提示。它单调递增。

判题实例**没有回退**：它是 reset → 回放 → 判定，一次性的纯函数，学习者不在中途操作它。想看自己的 payload 怎么跑的，用回放录像，见 §5.1。

- **P1**：命名 checkpoint。

## 4. 公开投影

每次响应都返回**完整投影**，不做增量。前端对相邻两次投影做差分，用于高亮变化。

| 字段 | 内容 |
|---|---|
| `status` | 实例状态，见 §1.1 |
| `steps` | 已执行指令数 |
| `failures` | 被拒绝 + 失败的动作计数，用于解锁提示 |
| `registers` | 全部寄存器，值为 hex 字符串；另含 `flags: {ZF, CF, SF}` |
| `vmas[]` | 全部 VMA 的布局 `{id, kind, label, start, size, perm, hidden}`；仅非隐藏的带 `hex` |
| `stdin` | `{hex, pos}`：已 `feed` 的全部字节和当前读位置。题目未声明 stdin 时省略 |
| `stdout` | `{hex}`：程序写到 stdout 的全部字节。题目未声明 stdout 时省略 |
| `disasm[]` | 服务端对非隐藏的 `x` 区域线性反汇编：`{addr, bytes, text, target?}` |
| `lastStop` | `{reason: exit\|exception\|limit\|step, addr?}` |
| `error?` | `{code, message, note}`，message 来自模板，note 来自题目 `errorNotes` |

- 投影里**没有 flag**。flag 只在提交判胜时由 `/submit` 返回，见 §5.1。
- 题目加载时校验可见字节总量上限（建议 256KB），保证全量投影代价可控。
- 被 `reveal` 的 VMA 在投影里变为 `hidden: false` 并带上 `hex`。
- 隐藏 VMA 的内容、虚拟文件内容、`win`/`fail` 永不出现在任何响应中。它们只能经由程序执行“获取”，见 02 §3。
- 断点没了之后 `limit` 从边缘情况变成常态：“运行 N 步”正常停下来就是这个原因。

## 5. REST API

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/challenges` | 题目列表：`[{id, title}]` |
| `GET` | `/api/challenges/:id` | 题目公开部分（`public.json`） |
| `POST` | `/api/sessions` | `{challengeId}` → `{sessionId, projection}` |
| `GET` | `/api/sessions/:id` | 调试实例的当前投影，用于刷新恢复 |
| `POST` | `/api/sessions/:id/actions` | `{actions: [...]}`，作用于调试实例，见下 |
| `POST` | `/api/sessions/:id/submit` | `{actions: [...]}`，作用于判题实例，见 §5.1 |
| `DELETE` | `/api/sessions/:id` | 主动结束会话 |

`actions` 批量接口（调试实例）：

- 按顺序执行，遇到第一个被拒绝的动作或进入 `failed`/`exited` 即停止，后续动作不执行。
- 返回 `{results: [{ok, error?}], executed, projection}`，`executed` 为实际执行的动作数。
- 整批只压一份请求层快照，见 §3。

### 5.1 提交判题

`POST /api/sessions/:id/submit`，请求体是编译好的完整动作序列。

服务端的处理是一个纯函数，不受调试实例影响：

1. 判题实例重置到题目初始状态。
2. 按顺序回放 `actions`。任一动作被拒绝即终止。
3. 按 `win` / `fail` 判定，`fail` 优先。

返回 `{verdict, executed, results, replay, flag?}`：

| 字段 | 内容 |
|---|---|
| `verdict` | `won` / `failed` / `rejected` / `incomplete` |
| `flag?` | 仅 `verdict = won` 时出现，取自私有包的 `flag` |
| `replay` | 回放录像，见下 |

- `incomplete` 指回放跑完了但成功条件未满足——payload 不够，不是写错了。这是最需要讲清楚的一种结果。
- **payload 必须自足。** 它从初始状态出发，所以不能依赖调试实例里的手工操作。偏移应该是学习者算出来的字面值，而不是“读取当前 RSP”这类积木——后者在初始状态下读不到调试时看见的那个值。05 §4 因此禁止 payload 含读状态积木。
- 提交不限次数，不压快照，不影响调试实例。

**回放录像。** 判题那次运行已经结束且有界，所以可以整段返回给前端拖着看：首份完整投影 + 逐动作 diff，避免几十份 256KB 投影把响应撑爆。这几乎免费地把原先推到 P1 的“时间线”在判题侧做出来了。录像只含公开投影，不泄露任何新东西。

flag 是每题固定值，不按会话生成。这意味着一旦有人公开 flag，其他人可以不做题直接提交。MVP 接受这个代价：新生赛的目标是学会，不是防串题。

- **P1**：按会话签名的一次性 token，用于真正需要防串题的场合。

## 6. 安全说明

- `sessionId` 为 128 位随机值，作为持有即可用的凭证（bearer capability），不可枚举。
- **MVP 不做用户认证**。部署到公网前需评估：任何人都能创建会话，进度不归属到人。
- 必须的防护：
  - 请求体大小上限、单批动作数上限、`run` 的 `maxSteps` 上限、`step` 的 `count` 上限。
  - 按 IP 限流；全局与每 IP 的并发会话数上限。提交接口单独限流：它每次都要跑一遍完整回放。
  - 错误响应不包含内部堆栈、文件路径或私有包字段。
- 一份会话含两个实例，内存占用翻倍，再加上指令层环形缓冲（§3）。并发上限要按这个量算。
- `private.json` 只在服务端读取，不放进静态资源目录。它本身进 git，但 flag 真值不进：`flag` 字段写 `"env:FLAG_<ID>"`，部署时由环境变量注入，见 [07](07-工程约定.md) §7。

## 7. 技术栈建议

全栈 TypeScript，单一服务同时承担 VM 引擎、API 和前端静态托管。详见 [07](07-工程约定.md)。

- 选择全 TS 而非 Rust 引擎的理由：指令集是小的封闭集，步数上限只有一万，Rust 的性能优势在这里用不上；而单一工具链和前后端共享类型能明显降低协作成本。
- 前端：Vite + Lit + Blockly。
- 编码表、`public.json` 与投影的类型定义放在前后端共享的包里，是单一事实来源。
