# 07 工程约定

## 1. 已定决策

| 项 | 决定 | 理由 |
|---|---|---|
| 后端语言 | 全栈 TypeScript，Fastify + 进程内 VM 引擎 | 指令集是小封闭集、步数上限一万，Rust 的性能优势用不上；单一工具链和共享类型显著降低协作成本 |
| 仓库结构 | pnpm workspace monorepo | 前后端共享类型，一次 `pnpm i` 起全栈 |
| flag | 每题固定值，判题判胜时随提交结果下发；真值由环境变量注入 | 新生赛目标是学会，不是防串题 |
| 快照粒度 | 三级回退，仅调试实例：重置 / 按请求撤销 / 按指令后退（环形缓冲 64 步） | 请求级契合“一次尝试”，指令级补上“给我看前一瞬间” |
| 会话存储 | 进程内内存，重启即丢 | 比赛期间不重启；加数据库的复杂度换不来价值 |
| 认证 | 无 | 仅限校园网或比赛期间开放，见 §5 |
| 界面语言 | 只做中文 | 面向新生赛 |
| 适配范围 | 桌面浏览器，最近两个大版本 | 做题需要宽屏，移动端不在场景内 |
| 提示代价 | 不扣分 | 提示是教学手段，不是惩罚 |

## 2. 仓库结构

```
packages/
├── shared/        # 类型与 Schema：public.json、投影、动作、编码表。单一事实来源
├── engine/        # VM 引擎：纯函数 + COW 内存，不依赖 HTTP
├── server/        # Fastify：会话管理、题目加载、REST API、静态托管
├── web/           # Vite + Lit + Blockly 单页应用
└── authoring/     # 出题 CLI：asm、check、solve、new
challenges/        # 题目包，见 06
presets/           # 默认编码表
docs/              # 本目录
```

依赖方向只能向左：`web` 和 `server` 依赖 `shared`，`server` 依赖 `engine`，`engine` 只依赖 `shared`。**`engine` 不许 import `server`**，否则引擎没法单独测。

## 3. 开发顺序

1. `shared`：类型与 Schema 先定，后面两边才有共同语言。
2. `engine`：取指、解码、执行、异常、COW 快照。全部用单元测试驱动，不需要起服务。
3. `authoring`：汇编器与校验 CLI。有了它才能开始出题。
4. 第一道题 `ret2win`（03 §4 已有完整示例），作为端到端的靶子。
5. `server`：会话、投影、REST。
6. `web`：先出栈视图和寄存器视图，再接积木窗口。
7. 剩余题目。协作者从第 4 步之后就可以并行出题。

第 3 步做完就能让协作者进场，不必等前端。

## 4. 测试

| 层 | 范围 | 要求 |
|---|---|---|
| 单元 | `engine` 的每条指令作用、每种异常、COW 快照 | 覆盖率 80%+。引擎是安全边界，这里不打折 |
| 单元 | `shared` 的 Schema 校验、`authoring` 的汇编器 | 正例与反例都要有 |
| 集成 | REST API：会话生命周期、动作批量、undo/reset | 覆盖每个终态 |
| 安全 | 见 §5 清单 | 每条都要有对应测试 |
| 题目 | 每道题的 `challenge:solve` | 全部通过才能合并 |
| E2E | Playwright 跑通 01 §3 的八步闭环 | 只做这一条主路径 |

引擎确定、不读时间、不用随机数，所以每个测试都能断言精确的内存与寄存器值。不要写模糊断言。

## 5. 安全测试清单

这几条对应 01 §6 的安全底线，必须有测试覆盖：

- 对隐藏 VMA 的 `write_bytes`，以及栈槽落在隐藏 VMA 时的 `pop` / `ret`，都回 `hidden_address`，状态不变，响应里不含任何隐藏字节。
- 投影里隐藏 VMA 只有布局、没有 `hex`，`disasm` 不覆盖隐藏区域；投影里不出现虚拟文件内容、`win`、`fail`。
- `reveal` 之后被 `undo` / `step_back` 回退，该 VMA 重新隐藏；stdin 读位置、stdout、文件读偏移一起回滚。
- `read` / `write` / `copy` 的 buf 有任何一字节越权，整个调用 `memory_fault` 且无副作用；`count` 超过 0x1000 时截断。
- `feed` 让 stdin 超过 4KB 被拒绝；stdout 超过 4KB 报 `resource_limit`。
- 调用号不在 syscall 表里报 `invalid_instruction`。
- 虚拟文件或隐藏 VMA 的内容包含 flag 真值时，该题拒绝加载。
- 调试实例的投影里永远没有 `flag` 字段，哪怕当前状态已满足成功条件。
- 调试实例里满足成功条件只回“已满足”，不下发 flag、不记录通过。
- 客户端提交的 `block` 展开结果被忽略，服务端自己展开。
- 伪造判胜结果或提交快照的请求被拒绝。
- 不在 `allowedActions` 里的动作被拒绝。
- payload 里出现读状态积木时，提交被 `rejected`，不是静默当成零。

### 5.1 七天内部试用冲刺的临时验收例外

按 [08-Agent并行开发日程.md](08-Agent并行开发日程.md) 的七天计划，交付物是**内部试用候选版**，不是完整 MVP 验收通过的版本：

- 01–06 的功能和安全实现要求不变；不删除权限校验、隐藏投影、双实例隔离、资源限制或服务端判胜。
- 本轮安全验收按 08 §5 的 S01–S06 六组核心检查执行，每组全部条件必须通过。（D3 收工时的实际状态见 [08](08-Agent并行开发日程.md) §8：S02 通过；S01/S03 部分、S04 部分（4 条为契约缺口）；S05/S06 **零断言**，D4–D5 补齐。**D4 收工时的实际状态**：六组条件**全部通过**——S01/S03/S04 逐条复核，S06 八条 todo 转真实断言，`it.fails` 归零；只剩 5 条 `todo` 且**全部是口径/运维项、不属于任何一组条件**（S04 的 `reads_state` ×3 与编译上限 ×1 属 09 §8 第 4–5 条的分层口径，S05 的加载失败告警是 D6 运维项）。六组之外的浏览器闭环仍未验。）
- **测试运行器的超时按真实负载给，不要用默认值**（D4 记）：本仓库的契约测试走真实 HTTP（`app.inject`）与真实引擎，单是 C03 的抽样穷举就要发 1000+ 次请求。vitest 默认 `testTimeout: 5000` 在**并行负载**下会把 8 条真实用例打成 `Error: Test timed out in 5000ms`（D4 用三份并发全量复现），**CI 因此会间歇性变红**。`vitest.config.ts` 已设 `testTimeout`/`hookTimeout` = 30s。这不是放宽断言：真挂死的用例照样失败，只是晚一点；把某条断言改坏仍然**立即**失败。
- 本节原清单第 3–6 条的专项黑盒测试暂缓：回退后的隐藏状态/I/O 联动恢复、syscall 越权原子性与 count 截断、I/O 容量边界、未知 syscall；补测任务见 T01–T04。
- 基础单元/集成测试仍需通过，引擎覆盖率仍为 80%+；已有测试不删除、不跳过，已知失败不能忽略。保留 typecheck、lint、全部题目 check/solve。
  - **真实闭环 E2E 目前不算已保留项**：`tests/e2e/closed-loop.spec.ts` 默认整组跳过（`PWN2BLOCK_E2E=1` 才执行），用例体是 `throw new Error('D5 待实现…')` 的骨架，`pnpm e2e` 报 9 skipped、0 executed。浏览器闭环按 08 的排期在 **D5** 真实验收，D3 的验收上限是「真实引擎 + 真实 HTTP」，不把这条骨架当作通过。
- 仅允许本机或隔离测试环境内部试用，使用测试 flag 与非敏感数据。缺少专项测试代表证据不足，不代表这些边界没有风险。
- 正式比赛或其他非隔离使用前，必须补齐 08 的 T01–T06，恢复本节全部测试并完成完整 MVP 验收。

此例外只改变七天候选版的验收范围；完整 MVP 仍执行 §4–§5 的完整基线，不把延期测试改为永久可选。

## 6. 协作约定

- 分支从 `main` 切出，一个 PR 一件事。出题 PR 只碰 `challenges/<id>/`。
- 提交信息用 `<type>: <description>`，type 取 feat / fix / refactor / docs / test / chore。
- CI 必须跑：typecheck、lint、单元测试、集成测试、全部题目的 `challenge:solve`。
- 改 `shared` 的类型时，同一个 PR 里把 `server` 和 `web` 一起改完。类型是契约，不留半截状态。
- 改引擎语义或 API 形状时，同步更新 02 / 03 / 04。文档和代码不一致，以代码为准并立刻修文档。

## 7. 部署

- 单进程：Fastify 同时提供 API 和 `web` 的构建产物。
- **静态托管的发布边界（D4 定，C04）**：构建产物挂在 `/`，默认静态根是仓库根的 `packages/web/dist`（可由 `buildApp` 的 `staticRoot` 覆盖，`serveStatic: false` 可整体关闭，见 04 §6、09 §4）。只服务该目录内的文件；`/api/**` 永远优先；**不做 SPA 回退**，未命中一律 404 `ApiError`（前端是单页、没有客户端路由）；不开启目录列表；点文件按「不存在」处理，`/.env` 得 404。`private.json` 与 `solution.md` 另有一层 basename 黑名单：即使被误拷进产物目录也取不到内容。
  - 这层黑名单**不是完备的敏感清单**（`flag.txt`、`secrets.json` 之类不在其中）。真正可验证的性质是「产物目录里只有构建产物」：S06 既检查静态 HTTP 路径，也检查产物目录内容；把私有材料放进 `dist` 本身就不合规。
  - 静态根缺失**不是启动错误**：静态请求逐条 404、`/api/**` 照常，所以本地只跑 API 时可以不起构建；但**跑 S06 的真实产物用例前必须先 `pnpm build`**（CI 的构建步骤已排在测试之前，否则那两条会被跳过而不是执行）。
- 必需的环境变量：`FLAG_<题目ID大写>` 每题一个，题目 id 里的 `-` 换成 `_`（`stack-frame-01` → `FLAG_STACK_FRAME_01`），缺失时该题拒绝加载。`challenge:check` 会拒绝 `flag` 字段不是这个形态的包（明文常量或变量名与 id 不匹配），见 [06](06-出题指南.md) §6。
- CI 与本地校验同样需要它：`challenge:check` / `challenge:solve` 共用服务端的加载校验，缺失就按设计报「环境变量缺失，拒绝加载该题」。CI 在 job 级注入**测试哨兵值**（`.github/workflows/ci.yml`，如 `FLAG_RET2WIN: pwn2block-ci-sentinel`），真 flag 绝不进仓库；本地照 `.env.example` 导出哨兵值。
- 建议放在反向代理后面，由代理做 TLS 和 IP 限流。
- **加载失败的可诊断性口径（D3 定）**：题目包加载失败时，对外的表现是 `503 challenge_unavailable` + 固定文案（不含命中位置、文件路径、私有包字段或堆栈），对**出题人/运维**的诊断入口是 `pnpm challenge:check --all`（与加载器共用同一份 `checkChallengePair`，能给出确切原因）。两者合起来即完整口径。服务端**不**为加载失败打日志，这是现状而非要求；补一条含题目 id 与原因的 `log.warn` 属运维改进（D6，owner C），不影响对外安全口径。
- 没有认证，所以不要长期挂在公网。比赛结束就关，或者限制在校园网内。
