# 09 契约冻结（D1 / G0）

> 依据 [08](08-Agent并行开发日程.md) 的 D1 关卡 **G0**：骨架、shared Schema、模块接口、API 样例、CLI 解法格式明确，基础检查通过。
> 本文件是**冻结契约的索引**，不是新需求。字段与类型的权威定义在 `packages/shared/src/**`；
> 本文件与代码不一致时以代码为准，并立刻改本文件。

## 1. 谁依赖谁

```
web ─┐
     ├─→ shared ←─ engine ←─ server
authoring ─┘        ↑
                 只依赖 shared，不许 import server（07 §2）
```

- `shared` 是类型与 Schema 的单一事实来源，不放文件 IO、不放 HTTP、不放引擎实现。
- 五个包都以 TS 源码互相引用（`exports` 指向 `src/index.ts`），不经过构建产物。

约定：
- **客户端提交的一切用 `strictObject`**：多余字段被拒绝而不是被静默丢弃（01 §6 第 3 条、S03）。

## 3. 关键接口（谁实现、谁消费）

### 3.1 B ↔ G（引擎内部）

| 契约 | 实现者 | 消费 |
|---|---|---|
| `MemoryApi`（`create/check/read/write/copy/readVma/snapshot/restore`） | G（`engine/src/memory`，入口导出名 `createMemory`） | B 的执行循环、快照编排 |
| 内存显隐 | **不在内存层**：程序指令可正常读写隐藏 VMA，可见性由 B（动作层拒绝）与 C（投影）负责 | B、C |

### 3.2 D ↔ H（前端内部）

| 契约 | 实现者 | 消费 |
|---|---|---|
| 归一化积木树 → `{ok, actions, origins, originsVersion}` 或 `{ok, errors:[{blockId, message}]}` | H（`web/src/compiler`） | D 在 D4 接入程序区、错误定位与录像定位 |

| 字节构造（`padding/string/int/addr/raw/concat`） | H（`web/src/compiler/bytes.ts`） | H 的编译产物 |

| 积木定义与挂载桥（`web/src/blocks/definitions.ts`、`mount.ts`） | H（**D2 已实现**）：定义由 `catalog.ts` 的 `BLOCK_SPECS` 生成 | D 在 `#blockly-host` 上调 `mountBlockly(host, challenge)`，用 `normalize()` 取积木树、`onChange` 触发重编译、`highlight(blockId)` 定位错误积木。**事件只覆盖用户手势**，程序化装载程序后要主动重编译（05 §3.1 实现备忘） |

本轮不做「列表」与「带返回值的函数」两类通用积木：payload 运行期没有计算能力，它们只能靠编译期内联/常量折叠，而内联语义（调用深度、递归上限）尚未定，先不做（D2 再定，见 [05](05-前端交互.md) §3.1）。

### 3.4 动作来源表与录像帧关联（D2 定稿，08 §9.2）

这两条都**不新增字段给网络契约**，只用前端内存里的来源表与已下发的录像：

**动作来源表（A/H/D 定，H 实现）**

```ts
interface ActionOrigin { readonly index: number; readonly blockId: string }
const ACTION_ORIGIN_VERSION = 1;
// CompileResult.ok = { actions, origins, originsVersion }
```

- 不变式：`origins.length === actions.length` 且 `origins[i].index === i`；`blockId` 是画布上真实存在的积木 id。
- 循环展开出的每个动作都指向**循环积木本身**；出题人积木产生的 `block` 动作指向那块出题人积木。
- **只活在前端内存里**：发往 `/actions` 与 `/submit` 的请求体只含 `actions`。
- 重新编译即重算来源表，不得跨编译复用；`originsVersion` 与当前版本不一致时按「来源未知」处理，不做猜测式定位。

**录像帧与提交动作的关联（A 定，C 核对，D 消费）**

`replaySubmit` 的帧序列是「`init` 一帧 + 每个提交动作一帧 `action` + 该动作触发的每条指令一帧 `instruction`」；`projectReplay` 把 `init` 摘为 `initial`，其余帧从 0 重新编号。因此：

- `replay.initial` = 初态，即第 1 个提交动作之前；
- `frames` 里 `kind === 'action'` 的帧，按出现顺序**第 k 个**对应第 k 个提交动作（1-based）；
- 两个 `action` 帧之间的 `instruction` 帧属于**前一个** `action` 帧；
- 被拒绝 / 失败的动作照样占一个 `action` 帧并带 `error`，其后回放终止；
- `frames[i].index` 是**帧序号**，不是动作下标；前端用来源表把动作下标映射回积木。
- 真实录像必须满足 `results.length === frames.filter(f => f.kind === 'action').length`，且第 k 个 `action` 帧的 `label` 等于 `results[k].action`。

**代码变化后的回放指令视图（A 定，D 实现，F 补用例）**

`ReplayFrame` 目前**不带** `disasm`（不给 shared 加字段，先按现有契约做）：

- 录像播放时指令视图显示 `replay.initial.disasm`，并且**仅当**该反汇编对整个回放仍然有效时才可使用；
- 判定方法：遍历 `frames[].changedVmas`，若出现 `perm` 含 `x` 的 VMA 内容变化，则说明代码在回放中被改写 → 指令区显示「录像中代码已变化，指令视图不可用」，**不许**继续显示过期反汇编；
- 前端不解码（03 §4 同一条约束）。若将来要逐帧正确反汇编，需给 `ReplayFrame` 加字段，由 A 收口并同批适配消费者。

### 3.3 引擎对外（C/E/F 消费）

- `createRuntime(pub, priv): EngineRuntime` 是引擎唯一入口（B 实现）。
- `EngineRuntime.replaySubmit(actions)` 是**纯提交回放**：从初态执行并判定终态，**不读也不发 flag**；C 的 `/submit` 与 E 的 `challenge:solve` 共用它，不另写判题器（08 §2 规则 4）。
- 投影、错误文案、反汇编都不在引擎里生成：引擎给结构化状态，服务端按白名单投影（04 §4）。

## 4. API 与投影要点

- 每次响应返回**完整投影**（`ProjectionSchema`）；`actions` 响应另带 `history: {undo, stepBack}`，前端据此禁用回退按钮并说明原因。
- 投影里没有 `flag`、没有 `win`/`fail`、没有虚拟文件内容；隐藏 VMA 只有布局。**调试实例满足成功条件也只回状态**。
- **投影带 `roles`（`{sp, bp, ip}`）**：D1 定下的契约决策（08 §8 阻塞 1、§9.2）。角色来自私有包，但属于「固定的东西」，随投影下发；前端不读私有包，也不硬编码 `RSP`/`RBP`/`RIP`。`public.json` 不重复声明。
- `/submit` 返回 `{verdict, executed, results, replay, flag?}`，`flag` 仅在 `verdict = won` 时出现；`replay` 是「首份完整投影 + 逐动作 diff」（`ReplaySchema`），只含公开投影。`replay.initial` 同样带 `roles`。
- 请求体上限、动作数上限、`step.count` / `run.maxSteps` 上限全部取自 `limits.ts`。

## 5. CLI 与题目包格式

- 子命令：`new / asm / check / solve`（06 §2）。`check` 与 `solve --all` 在没有题目包时返回 0，一旦有题目包就必须真实执行，未实现的路径**非零退出**而不是假装通过。
- `solution.md` 必须含且仅含一个 ```json 块：`{actions, expectedVerdict?, note?}`，解析器在 `shared/src/solution.ts`（06 §2.3）。
- flag 真值只经环境变量注入（`flag: "env:FLAG_<ID>"`），缺失即拒绝加载该题；虚拟文件与隐藏 VMA 内容包含 flag 真值同样拒绝加载。

## 6. 冻结后的变更规则

- 任何人不得在并行期间直改 `packages/shared/**`；需要新字段或改形状时向 A 提「契约缺口」。
- shared 形状变更必须**同一个提交里**把 engine / server / web / authoring 的消费者一起改完（07 §6），不留半截状态。
- 改引擎语义或 API 形状，同步 `docs/02`/`03`/`04`，并在 `docs/08` 的当日记录里写明。

## 7. D1 实现期定稿的语义澄清

B 在实现执行循环时遇到 04/02 没写清的地方，逐条定稿如下（改的是解释，不是需求）：

| # | 澄清 | 依据 |
|---|---|---|
| 1 | 动作 `pop` 读栈槽校验通过后**丢弃值**，只把 `sp` 前移 W：它是弹栈动作，没有目标寄存器 | 04 §2 |
| 2 | 动作 `call addr` 压入的是**当前 ip**（不是下一条）：它不执行指令，没有"下一条" | 04 §2 |
| 3 | 命中 `fail` 谓词时 `lastStop.reason = 'exception'` 且**不带 `error`**：这是判负不是运行期异常；`stop` 枚举里只有它不属于 `step`，否则取指循环会继续跑 | 02 §6、04 §4 |
| 4 | `executed` 计数：`step`/`run` 的结果里是指令数；`actions`/`submit` 响应里是**实际生效的动作数**（被拒不计，一个 `block` 算一个） | 04 §5 |
| 5 | `satisfied` 不限制任何动作（04 §1.1 原文）：置 FLAG 后仍可继续写内存或执行，只有 `failed` / `exited` 中断批量 | 04 §1.1 |
| 6 | 取指语义按 x86：先 `ip += 指令长度` 再执行控制转移，所以 `syscall` 之后 ip 指向下一条，`jmp` 到自身不会前移 | 02 §4 |
| 7 | `disasm` 扫描范围 = 最后一个 init 补丁末尾 ∪ 最后一个非零字节：否则空白页会下发 4096 条 `db 0x00`；最后一个有效字节是半个指令时如实报 `db` | 02 §4 |
| 8 | 内存 `check/read/write` 的 `len === 0` 一律通过且不触碰字节：零长度没有信息量，不能当映射探测用 | 02 §3 |
| 9 | `MemResult.ok.bytes`：`read` 是读到的字节，`write` 是写入字节的副本，`copy` 是拷出的源字节副本；写类操作只看 `ok` 也成立 | shared `vm.ts` |
