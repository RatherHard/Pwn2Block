## 1. 运行条件与源码事实

需要 Git、Node.js 和 pnpm。根 `package.json` 声明 Node `>=22`、`packageManager: pnpm@11.25.0`；本次实际使用 Windows PowerShell、Node `v24.20.0`、pnpm `11.25.0`。优先采用已验证的版本；本文不宣称所有满足 Node 范围的版本都已验证。预先准备这些工具，并让安装能访问依赖源或完整的本机 pnpm 缓存。

从仓库根执行命令。保留整个 checkout、workspace 依赖、`challenges/` 和 `presets/`：`pnpm build` 只构建前端，`pnpm start` 仍通过开发依赖 `tsx` 执行 TypeScript 源码，不是运行一个编译好的服务端二进制。不要使用 `pnpm install --prod` 或只复制 `dist` 就尝试启动服务。

| 项目 | 当前实现与依据 |
|---|---|
| 启动 | 根 `package.json`：`pnpm start` → `tsx packages/server/src/index.ts` |
| 端口 | `packages/server/src/index.ts`：`Number.parseInt(process.env.PORT ?? String(DEFAULT_PORT), 10)`，默认 `8787`；本次独占 `8798` |
| 地址 | 同一入口固定 `host: '127.0.0.1'`；设置 `HOST` 不会改变监听地址 |

| 其他配置 | `buildApp` 的 `sessions`、`rateLimit`、`challengeDir`、`presetDir`、`staticRoot`、`serveStatic` 是代码调用参数，启动脚本没有把它们映射为环境变量 |

入口没有完整的端口格式校验，应自行给 `PORT` 一个合法、空闲的 TCP 端口。不要依赖无效字符串的转换行为。

### `.env` 不会由服务端自动加载

已核对根启动脚本、`server/src/index.ts`、`app.ts` 与 `challenges.ts`：启动链没有 `dotenv`、`loadEnvFile` 或 `--env-file`。**复制 `.env.example` 为根目录 `.env`，再执行 `pnpm start`，不会注入这些变量。** `.gitignore` 排除 `.env` 只防止误提交，不负责加载。

本文主流程显式设置 shell 进程环境，再运行 `pnpm start`，不读取真实 `.env`。`.env.example` 含 `PORT` 和六个假 flag。可选的显式加载方式是从仓库根运行：

```text
node --env-file=.env.example --import tsx packages/server/src/index.ts
```

这是直接运行 Node 的另一条启动命令，不是 `pnpm start` 的自动行为。Node 已有进程环境优先于文件中的同名值；使用本次端口时先设置 `PORT=8798`。不要给 flag 加 `VITE_` 前缀或写入前端配置；前端构建的环境处理与服务端启动是两条独立流程。

## 2. 干净 checkout 到安装、构建、启动

准备新的 checkout，以下占位符须替换成实际仓库来源与待验收提交。仓库来源可以是本地仓库路径；若已经在干净 checkout 根目录，跳过 clone/cd/checkout。先确认 `git status --short` 无输出，并记录 `git rev-parse HEAD`。本次基线是上文的 `8a40600`，后续整合交付应记录实际整合版本。

```text
git clone '<仓库地址或本地仓库路径>' Pwn2Block
cd Pwn2Block
git checkout --detach '<待验收提交号>'
git status --short
git rev-parse HEAD
```

不要覆盖已有工作区，也不要用删除锁文件、非冻结安装或更新依赖来绕过安装失败。检查命令成功后再进入下一步。

### Windows PowerShell

在专用终端、仓库根目录执行。清除当前子流程的 `NODE_OPTIONS`，避免继承预加载器或环境文件选项；不读取或打印已有环境变量值。

```powershell
$env:NODE_OPTIONS = ''
node --version
pnpm --version
pnpm install --frozen-lockfile
if ($LASTEXITCODE -ne 0) { throw '依赖安装失败，停止部署' }
pnpm build
if ($LASTEXITCODE -ne 0) { throw '前端构建失败，停止部署' }
if (-not (Test-Path -LiteralPath 'packages/web/dist/index.html')) {
    throw '缺少前端产物，停止部署'
}

$env:PORT = '8798'
$env:FLAG_RET2WIN = 'flag{local-test-sentinel}'
$env:FLAG_ENDIAN = 'flag{local-test-sentinel}'
$env:FLAG_PUSHPOP = 'flag{local-test-sentinel}'
$env:FLAG_CALLRET = 'flag{local-test-sentinel}'
$env:FLAG_STACKFRAME = 'flag{local-test-sentinel}'
$env:FLAG_LOCALVAR = 'flag{local-test-sentinel}'
pnpm start
```

保持该终端运行。另开终端执行无状态检查：

```powershell
Invoke-RestMethod 'http://127.0.0.1:8798/api/health'
Invoke-RestMethod 'http://127.0.0.1:8798/api/challenges'
(Invoke-WebRequest -UseBasicParsing 'http://127.0.0.1:8798/').StatusCode
```

```sh

curl --fail --silent --show-error http://127.0.0.1:8798/api/challenges
curl --fail --silent --show-error --output /dev/null --write-out '%{http_code}\n' http://127.0.0.1:8798/
```

健康接口只表明服务响应，不能证明六题可用或前端已构建。还应检查首页引用的 `/assets/*.js` 返回 200；静态根缺失时 API 仍可用，首页会 404。静态根不要改为仓库根，不复制题目私有材料、环境文件或解答进去。未命中路径返回 404，没有 SPA 路由回退。

## 3. 缺 flag 的行为与恢复

六个变量名由现有六份 `challenges/<id>/private.json` 的 `flag` 字段决定，与 `.env.example` 一一对应。缺失或空字符串会让该题加载失败：

- 启动记录 `event: challenge_load_failed`、对应 `challengeId`、`reason: flag_missing`。
- `GET /api/challenges` 不包含该题；健康接口仍然返回 200，其他配置正确的题仍可使用。
- 获取该题公开详情或为它建会话返回 HTTP 503、`code: challenge_unavailable`；不是整个服务启动失败。

可在停止服务后，仅移除一个本次假变量来复核：PowerShell 用 `Remove-Item Env:FLAG_LOCALVAR -ErrorAction SilentlyContinue`，POSIX 用 `unset FLAG_LOCALVAR`；其余五个假变量与 `PORT=8798` 保持不变，再运行 `pnpm start`。若采用显式 `--env-file=.env.example`，文件会重新提供该变量，因此缺 flag 演练必须使用 shell 环境版 `pnpm start`。

复核完成后停止服务，重新设置该假变量并启动。题目在启动时加载，没有配置热重载；修改另一个终端的环境也不会改变已经运行的服务。不要为了恢复可用性填写真 flag。本次仅检查配置和会话生命周期，不执行题目解法或新增攻击用例。

## 4. 会话过期、刷新与重启

服务端会话保存在单进程内存，默认空闲阈值 30 分钟（`SESSION_IDLE_MS`），定时清理周期 15 分钟。新建会话前也会回收空闲会话。回收是惰性的：达到阈值但尚未清理的会话仍可能被访问并刷新活跃时间，不能承诺“第 30 分钟精确失效”。这些时间不是同名环境变量可调的启动参数。

回收后访问会话返回 HTTP 404、`session_expired`；过期 id 的记忆有上限，较早的 id 也可能成为 `not_found`。重启会丢失全部会话和限流计数，旧 id 返回 HTTP 404、`not_found`，没有数据库、自动还原或跨进程共享。已通过记录也没有跨进程持久化保证。

浏览器刷新与进程重启须区别处理：

- 服务仍运行、会话存活时，前端先恢复本地画布，再 GET 会话接回服务器状态；程序区指针由本地记录恢复并校验。
- 服务回收或重启后，前端把会话接口的 404 识别为会话失效，提示点“重新开始”。这会创建同一道题的新会话，不能找回旧 VM、回退历史或执行进度。
- 本地画布可用时仍可继续编辑，但依赖同一浏览器、同一 origin 的本地存储。更换端口/主机名、清理存储或浏览器限制都可能使存档不可用；本地画布不是服务端备份。保留需要的画布后再停止服务。

行为依据为 `server/src/sessions.ts`、`app.ts`、`web/src/api.ts`、`web/src/viewmodel/controller.ts` 与 [04 §1](04-会话与API.md)。

## 5. 停止与已知边界

前台运行时在启动终端按 Ctrl+C。若终端异常，先使用启动日志里的 `pid` 核实本次进程，再按该 PID 停止：PowerShell `Stop-Process -Id <本次服务PID>`，POSIX `kill <本次服务PID>`。不要按名称批量结束 node，也不要结束其他协作者的进程。停止后确认 8798 的健康请求连接失败；若仍响应，先核对占用来源。

入口没有安装 SIGINT/SIGTERM 到 `app.close()` 的优雅关闭处理，不保证等待进行中的请求结束或保存会话。重新启动前重设 shell 环境；部署窗口内会话丢失是现有边界。专用终端用完即可关闭，避免把演练变量带入其他任务。

当前实现还有以下限制：

- 固定绑定本机，无认证和多实例共享会话，本文不提供公网或多节点部署方案。
- 默认普通 API 限流为 600 次/分钟/IP，提交单独 60 次/分钟/IP；存活会话每 IP 32、全局 128。静态资源与健康接口不计入。限流按 socket 地址，`trustProxy` 未开启；代理后可能共用同一 IP 配额，不能把代理头当作已支持的客户端身份配置。
- 前端本次构建有单包大于 500 kB 的警告；构建成功不等于完成浏览器验收或性能验收。
- T01–T06 仍按下表延期，已有单测/覆盖率不能替代专项组合证据。限制为内部隔离试用也不表示风险已消失。
